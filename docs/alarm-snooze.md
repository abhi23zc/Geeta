# Single-use alarm snooze

Regular alarms offer one five-minute snooze on the React wake screen and native fallback. Test alarms do not. Snooze is enforced by native state tied to the original occurrence and configuration revision, with a separate AlarmManager request identifier. Scheduling, persisted retry state, and presentation release must succeed before playback stops. Failure leaves playback running and the action retryable.

Volume Up and Volume Down use the same snooze allowance while Android delivers keys to the active wake activity, including its lock-screen presentation. The first key-down requests snooze; repeats and the matching release are consumed even after playback stops. After the retry rings, each new press shows the translated “Snooze already used” message and keeps ringing. Test alarms and Volume Mute retain volume blocking without snoozing. Pending native and React Start my day holds are cancelled before a hardware snooze attempt. Keys owned by another app are outside this handling.

Snooze ends the wake presentation without awarding rewards. The retry retains the original occurrence and reward receipt; the volume ramp restarts at 8% and reaches full player gain after two minutes. Home displays the pending retry time. The one-use marker remains after delivery. Editing or disabling the alarm cancels the retry; recurring alarms retain their independent schedule. A new regular occurrence supersedes an older pending snooze.

Device-protected storage retains the pending time across process death and reboot. Reconciliation and boot/time-change receivers rearm a pending retry when required access is available. Overdue retries are scheduled promptly once access is restored; consumed retries are not restored.

Before release, verify the five-minute retry while backgrounded and locked, process recreation and reboot, permission restoration, duplicate taps, second-snooze rejection, native fallback with delayed React startup, cancellation on edits, original recurrence, and exactly-once ritual rewards. Native policy tests cover one-use eligibility, stale/revised occurrences, due time, and failure-before-stop ordering. Hardware delivery has not been verified by source compilation or unit tests. No APK should be built or installed without authorization.

Volume press unit tests cover both keys, held repeats and release after snoozing, overlapping keys, duplicate downs, retry after failure, and rapid alternating requests sharing the used occurrence with an on-screen request. Navigation regressions cover Home restoration after snooze and cancellation of a pending Home exit when a newer alarm starts. Native unit tests, instrumentation-source compilation, TypeScript, scoped lint, and the alarm navigation suite pass. Device testing must still cover both activities, simultaneous button/hardware presses, translated feedback, and lock-screen key delivery.
